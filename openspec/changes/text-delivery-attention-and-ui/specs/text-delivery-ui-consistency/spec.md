## Purpose

使桌面、移动和 Web 在设备定向的文本投递流程中呈现同一套可理解的信息层级、状态语义与可访问交互，同时保留各宿主适配屏幕与输入方式的空间。

## ADDED Requirements

### Requirement: 三端文本编辑器遵循一致的信息与交互契约

在用户选定接收设备后的发送流程中，桌面、移动和 Web SHALL 以一致顺序呈现内容类型选择、文本编辑、显式粘贴、字节限制、最近发送状态和提交操作。文件/文本类型选择 SHALL 使用相同的标签、图标语义和紧凑等宽视觉规则；平台不得以整行拉伸与内容宽度两种冲突规则表达同一个控件。

#### Scenario: 用户切换到文本模式

- **WHEN** 用户在任一宿主的设备定向发送流程中选择“文本”
- **THEN** 系统 MUST 展示可编辑文本、显式粘贴入口、清空入口、统一的字节限制和发送操作
- **AND** 文件与文本选择控件 MUST 与其他宿主使用相同的标签和图标语义

#### Scenario: 不同可用宽度下呈现模式选择

- **WHEN** 三端分别在窄屏或宽屏展示文件/文本选择
- **THEN** 两个选项 MUST 保持相等的可点击宽度和紧凑的内容尺寸
- **AND** 选择控件 MUST NOT 因宿主不同而在“整行均分”与“按内容收缩”之间改变语义

### Requirement: 文本字节限制与发送结果以统一语义呈现

文本编辑器 SHALL 用 UTF-8 字节数计算限制，并在三端以同一 `KiB` 单位、同一上限与可本地化的状态文案呈现。发送结果和最近发送记录 SHALL 使用相同的状态名称、可重试性与错误表达；成功、等待确认、拒绝和失败不得被混为同一状态。

#### Scenario: 文本接近或超过上限

- **WHEN** 用户输入的 UTF-8 文本接近或超过允许上限
- **THEN** 系统 MUST 显示当前字节数与统一的 `KiB` 上限
- **AND** 超过上限时 MUST 阻止发送并提供可理解的错误状态

#### Scenario: 查看最近发送的文本

- **WHEN** 用户在任一宿主查看最近文本发送记录
- **THEN** 每条记录 MUST 以一致的状态语义显示投递结果
- **AND** 可重试的失败记录 MUST 提供明确且可达的重试操作

### Requirement: 文本接收表面保持跨端可访问与可定位

文本确认面板、自动接收反馈和收件箱入口 SHALL 使用一致的标题、来源设备、状态和动作语义。无论用户使用键盘、读屏、触摸或指针，都 MUST 能完成确认、拒绝、查看收件箱和复制已接收文本等可用动作。

#### Scenario: 用户从接收反馈进入文本收件箱

- **WHEN** 用户激活任一宿主的文本接收反馈或后台通知
- **THEN** 系统 MUST 导向包含该文本的收件箱上下文
- **AND** 焦点或读屏上下文 MUST 落在可理解的页面标题或对应文本条目上

#### Scenario: 键盘处理文本确认

- **WHEN** 桌面或 Web 用户通过键盘打开文本确认面板
- **THEN** 焦点 MUST 限制在该面板的可交互元素内
- **AND** 接受与拒绝操作 MUST 可通过键盘到达和触发
