## Why

文本投递已经具备可靠的收发与账本能力，但接收端仍主要依赖用户进入收件箱后的轮询发现；需要人工确认的文本也缺少即时、可控的注意力路径。与此同时，桌面与 Web 的文本发送界面在模式切换、层级、尺寸单位和提交区上表达不一致，削弱了三端作为同一产品的可预期性。

本变更将文本投递的“到达、确认、回看”从被动轮询升级为事件驱动的跨端体验，并在不扩展为全产品 UI 审计的前提下，收敛文本发送和接收相关表面的视觉与交互契约。

## What Changes

- 新增文本投递注意力能力：核心在文本投递持久化与状态转换后发布带稳定投递标识的领域事件；前端以事件为主、以低频同步为兜底，避免把轮询作为唯一到达提示机制。
- 在桌面、移动和 Web 提供一致的前台接收体验：需要确认的文本以单一、不堆叠的专用确认面板呈现，并能明确接受或拒绝；自动接收的文本刷新收件箱并提供非阻断反馈，而不误弹确认面板。
- 桌面应用在窗口不处于前台时使用系统原生通知提醒新文本；通知默认不暴露正文，点击后导向应用内收件箱。
- Web 在用户主动授权且当前页面仍存活时，于页面隐藏或未聚焦时使用浏览器通知；未授权、不支持或页面已关闭时优雅降级为应用内提示与下次打开后的收件箱状态，不承诺无服务器的离线推送。
- 收敛桌面、Web 与移动的文本编辑器信息架构：文件/文本模式控制、标题与辅助文案、显式粘贴、字节计数（统一 `KiB` 语义）、最近发送记录和提交操作采用同一交互与状态契约，并允许各宿主按屏幕形态实现布局。
- **BREAKING**：重组 `crates/transfer/src` 中平铺的文本投递实现，建立按文本投递领域划分的模块边界；文本 wire、状态机、服务和事件从泛化或平铺模块迁移到该边界，不保留旧模块路径兼容层。
- 明确不在本变更扫描或重做全部三端 UI 信息架构；全产品的一致性审计与治理将作为后续独立 change。移动端本次仅收敛应用内注意力与文本编辑体验，不新增移动系统后台通知。

## Capabilities

### New Capabilities

- `text-delivery-attention`: 定义文本投递的事件驱动注意力、前台确认、桌面原生通知与 Web 浏览器通知的隐私和降级语义。
- `text-delivery-ui-consistency`: 定义三端设备定向文本发送及文本接收注意力表面的统一信息层级、交互状态与可访问性契约。

### Modified Capabilities

- `drop-inbox`: 扩展文本收件箱条目的到达后刷新、定位与用户可见状态语义。

## Impact

- 影响 `crates/transfer` 的文本协议、状态机、服务和事件模块，及其测试布局；同时影响 core 的事件桥接和各宿主的收件箱同步入口。
- 影响桌面 Tauri 的事件订阅、窗口焦点判定与原生通知映射，Web 应用的权限设置、浏览器通知适配和可见性处理，以及移动端的应用内确认与收件箱刷新界面。
- 不引入账号、云服务、Push 服务或常驻后台 Web 接收器；Web 页面关闭后仍无法凭浏览器通知独立保持 P2P 接收。
