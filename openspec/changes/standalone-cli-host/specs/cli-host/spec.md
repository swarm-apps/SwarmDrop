## Purpose

把 SwarmDrop 的设备网络能力提供为一个独立的命令行宿主，使开发者与任何能执行命令的
外部程序（AI agent harness、脚本、服务管理器）无需安装图形界面即可完成配对、发送与接收。

## ADDED Requirements

### Requirement: 节点生命周期显式可控

CLI SHALL 提供 `start`、`stop`、`status` 三条命令，其节点状态语义与其余宿主一致：
节点只有 `Running` 与 `Stopped` 两态。

CLI MUST NOT 在任何情况下把一个已被用户停止的节点隐式恢复为常驻运行。

#### Scenario: 启动常驻节点

- **WHEN** 用户执行 `start` 且当前无节点在运行
- **THEN** 节点进入 `Running`，并持续在线直到被停止

#### Scenario: 停止节点

- **WHEN** 用户执行 `stop` 且有节点在运行
- **THEN** 该节点关闭，状态变为 `Stopped`

#### Scenario: 停止时无节点在运行

- **WHEN** 用户执行 `stop` 且当前无节点在运行
- **THEN** 命令以成功退出码结束并说明当前已是停止状态，不产生错误

#### Scenario: 查询状态

- **WHEN** 用户执行 `status`
- **THEN** 输出包含节点状态、本机节点标识、监听地址、NAT 状态与中继可达性

### Requirement: start 默认前台运行

`start` SHALL 默认在前台运行并阻塞，直到收到停止请求或终止信号；
SHALL 提供一个显式选项使其转入后台运行。

前台形态是服务管理器与外部程序托管子进程时的必要形态。

#### Scenario: 前台启动可被信号终止

- **WHEN** 前台运行的 `start` 收到终止信号
- **THEN** 节点执行有序关闭后进程退出

#### Scenario: 后台启动立即返回

- **WHEN** 用户以后台选项执行 `start`
- **THEN** 命令在节点就绪后立即返回，节点继续在后台运行

#### Scenario: 后台节点可被另一终端停止

- **WHEN** 节点以后台方式运行，用户在另一个终端执行 `stop`
- **THEN** 该节点关闭

### Requirement: 一次性命令使用临时节点

当没有节点在运行时，需要网络的一次性命令（如发送）SHALL 自行启动一个临时节点，
并在命令结束时销毁它。

临时节点 MUST NOT 改变「用户是否希望节点常驻」这一意图：命令结束后状态回到 `Stopped`。

#### Scenario: 无常驻节点时发送

- **WHEN** 无节点在运行，用户执行发送命令
- **THEN** 命令自行建立网络连接完成发送
- **AND** 命令结束后节点不再运行

#### Scenario: 临时节点期间的状态查询

- **WHEN** 临时节点正在运行期间查询状态
- **THEN** 状态为 `Running`，因为该设备此刻确实在线

### Requirement: 同一身份同时只存在一个节点

CLI SHALL 保证同一份数据目录在任一时刻最多有一个进程持有运行中的节点。

同一设备身份被两个进程同时用于上线会导致对端可达性记录互相覆盖、中继预留互相顶替，
因此该约束是正确性要求而非优化。

#### Scenario: 重复启动被拒绝

- **WHEN** 已有节点在运行，用户再次执行 `start`
- **THEN** 命令以错误退出码结束并说明节点已在运行，不启动第二个节点

#### Scenario: 常驻节点存在时执行其他命令

- **WHEN** 已有节点在运行，用户执行发送、设备列表或收件箱命令
- **THEN** 该命令复用正在运行的节点完成操作，不启动第二个节点

#### Scenario: 陈旧的通道残留不阻塞启动

- **WHEN** 上一个持有节点的进程异常终止并遗留了无法连接的本地通道
- **THEN** 下一次 `start` 判定其为失效并正常启动，不需要用户手工清理

### Requirement: 独立的设备身份

CLI SHALL 使用自己的设备身份与自己的数据目录，与同一台机器上的图形界面宿主互不共享。

CLI 的默认设备名 SHALL 能让用户在设备列表中将其与同机的图形界面宿主区分开。

#### Scenario: 与同机桌面端并存

- **WHEN** 同一台机器上桌面端与 CLI 都在运行
- **THEN** 两者各自以不同的设备标识在网络中出现，互不干扰

#### Scenario: 独立配对

- **WHEN** 用户已在桌面端完成与某设备的配对，随后首次使用 CLI
- **THEN** CLI 不继承该配对关系，需要单独完成配对

### Requirement: 接收不是一条命令

CLI MUST NOT 提供以「接收」为动作的命令。接收 SHALL 是节点在线时的被动后台行为，
与其余宿主的「配对 + 被动接收」模型一致。

#### Scenario: 常驻期间自动接收

- **WHEN** 节点处于 `Running` 且已配对设备向本机发送文件
- **THEN** 传输按既有的接收策略进行，无需用户执行任何接收命令

### Requirement: 配对邀请在终端可扫可复制

配对命令 SHALL 同时输出可扫描的二维码与可复制的邀请链接，
并 SHALL 提供关闭二维码渲染的选项以适应非交互环境。

#### Scenario: 交互式终端生成邀请

- **WHEN** 用户在交互式终端执行配对生成
- **THEN** 输出包含二维码与邀请链接

#### Scenario: 关闭二维码

- **WHEN** 用户以关闭二维码的选项执行配对生成
- **THEN** 输出只包含邀请链接，不含二维码图形

#### Scenario: 接受邀请

- **WHEN** 用户以一个邀请链接执行配对
- **THEN** 完成配对握手，之后该对端出现在设备列表中

### Requirement: 结构化输出模式

每条产出数据的命令 SHALL 支持一个结构化输出模式，其输出为机器可解析的格式并写入标准输出；
人类可读的进度与诊断信息 SHALL 写入标准错误，不污染结构化输出。

该模式是外部程序（agent harness、脚本）消费 CLI 的前提。

#### Scenario: 结构化输出可被解析

- **WHEN** 以结构化模式执行设备列表或状态命令
- **THEN** 标准输出是完整且可解析的结构化数据

#### Scenario: 进度不污染标准输出

- **WHEN** 以结构化模式执行发送命令
- **THEN** 传输进度写入标准错误，标准输出只含最终的结构化结果

### Requirement: 退出码区分失败原因

CLI SHALL 以退出码区分成功与不同类别的失败，使脚本无需解析文本即可判断结果。

至少 SHALL 区分：成功、用法错误、节点未就绪或不可用、对端不可达、传输失败、被用户中止。

#### Scenario: 成功

- **WHEN** 命令按预期完成
- **THEN** 退出码为 0

#### Scenario: 对端不可达

- **WHEN** 发送目标设备当前无法建立连接
- **THEN** 退出码为「对端不可达」类别，且与传输过程中失败的退出码不同
