## 11. 配对确认（2026-08-19，推翻 10.2 的策略）

第 10 节把「邀请 ⇒ 自动接受」当成了正确策略，**那是错的**：邀请只回答「这个请求不是凭空
捏造的」，回答不了「出示它的是不是我要配的那台」。它会泄露（截图、投屏、旁人抢先扫码），
且是一次性的——被抢走那次会消耗掉凭证，真正的设备再来就用不了。默认必须由人确认。

- [x] 11.1 默认不再自动接受：入站请求展示对端信息并等人确认（dialoguer，只在有终端时）
- [x] 11.2 展示信息足以分辨设备：完整节点标识（不截断）+ 设备名 + 系统 + **链路类型**
      （局域网直连 / 打洞 / 经中继 —— 回答「这台设备是不是真在我身边」）
- [x] 11.3 拒绝不消耗邀请，命令继续等待下一次请求
- [x] 11.4 配对窗口只在 `pair` 运行时打开：常驻节点把请求经本地通道转交给正在轮询的客户端，
      无人等待时一律拒绝
- [x] 11.5 `--auto-accept` 作为显式的风险交换（`start` 与 `pair` 都有）；未开启且无法交互时
      **在生成邀请之前**报用法错误
- [x] 11.6 修默认设备名：`OsInfo::default().hostname` 在 macOS/Linux 上必然是 `Device`
      （`HOSTNAME` 不是导出的环境变量），改用 `whoami::devicename()`
- [x] 11.7 压住第三方库的常态 WARN（`libp2p_mdns` / `rtc` / `webrtc`）——实测确认框
      出现不到一秒就被它们顶出可视区
- [x] 11.8 真机验证（vhs 提供真 TTY）：确认框显示完整、输入 y 配对成功、输入 n 拒绝后
      命令继续等待且对端收到退出码 6
- [x] 11.9 真机验证安全属性：常驻节点 + 无人等待 → 有效邀请被拒（退出码 6）；
      随后打开窗口，**同一张被拒过的邀请**配对成功，证明拒绝不消费凭证

## 12. 四路并行审查的落实（2026-08-19）

按 `/dev-workflow` 的 3.2 → 3.3 派了四个 agent 分审（复用与简化 / 并发正确性 / 安全策略 /
分层与项目约定），逐条落实：

- [x] 12.1 **数据目录收紧到 0700**。`identity.json` 是 0600，但本地通道套接字按 umask
      落成 0755——同机**其他用户**能连上它启停节点、列设备、发文件、应答配对。
      这是本轮唯一一条突破了「防其他用户」这条既定承诺的问题。两条护栏测试看守
- [x] 12.2 **处理期间检测对端断开**。`accept_one` 的任务与连接存活脱钩，客户端被 Ctrl-C
      掉之后它还占着确认台名额与接收锁到超时，期间到达的配对请求被它取走并写进已关闭的
      连接、就此消失，新的 `pair` 还得排它后面。护栏测试用 `Arc` 探针观察 future 是否被丢弃
- [x] 12.3 **Ctrl-C 改为只注册一次的监听**。`select!` 每轮重建 `ctrl_c()`，另一分支胜出时
      注册被丢弃，而 tokio 在无监听者时无条件清 pending——确认提示期间 dialoguer 补发的
      SIGINT 正好落在这个空档里。表现是按了 Ctrl-C 只等到「已拒绝」，要再按一次才退得掉
- [x] 12.4 `prompt::confirm` 返回 `Option<bool>`：**「读不到回答」与「答否」分开**，
      否则屏幕上「已拒绝，仍在等待」与紧随的「已中止」自相矛盾
- [x] 12.5 统一 `PairRespond` 的线协议为 `Data{PairOutcome}`（此前拒绝走无负载的 `Ok`，
      与 `PairAccept` 那条路径对同一件事有两种表达），并删掉 `Answered` 这层
- [x] 12.6 合并 `serve_locally` / `serve_via_daemon` 为一条循环 + `Desk` 枚举，
      两条路径的差别收敛到「取请求」与「送答复」两步
- [x] 12.7 删掉与 `bool` 同构的 `Disposition`；`render_waiting` 首行去重；
      空设备名兜底与 `render_paired` 对齐
- [x] 12.8 文档漂移：`main.rs` 的分层条数、`ipc.rs` 的「动词一一对应」措辞、
      知识库补 `start --auto-accept`、spec 补两个 scenario
- [x] 12.9 `pair --auto-accept` 的帮助文本改为「任一有效邀请」——实现从不核对
      capability，此前写「这张邀请」比实际范围窄。要收窄，前提是先有邀请撤销入口
- [x] 12.10 重跑四条端到端路径（vhs 真 TTY）：接受 / 拒绝后继续等 / Ctrl-C 退出（130）/
      常驻节点窗口关闭被拒（6）与打开后同一张邀请配对成功

**明确不做的一条**：本地通道无认证，同用户的其他进程可以直接发 `PairRespond` 接受一次
入站配对而不弹任何界面。这与本仓既定形态一致——那类进程本来就能读走明文私钥并冒充这台
设备，给通道加一次性 token 不改变实际攻击面，只会让人误以为它防住了什么。判据已写进
`runtime/ipc.rs` 的「信任边界」一节。
