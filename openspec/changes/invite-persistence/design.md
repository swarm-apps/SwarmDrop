# invite-persistence 设计

`pair-invite-protocol/design.md` D4 当时写的是「内存态（重启丢邀请是可接受语义）」——
那个判断在「邀请只用于当面扫码」的前提下成立。`invite-url-canonical` 改掉了这个前提，
所以这里推翻它。

## D1：单一 profile 拉长 TTL，不做双 profile

TTL 300s → 24h，一种 invite 一种语义。

备选（未采纳）：近场 300s + 内存态 / 远程 24h + 落盘，两种 profile。
否决理由 —— 分支会长在**四个地方**：wire（要有字段区分）、注册表（两套存储路径）、
生成 UI（用户得选一种）、撤销列表（两种来源）。换来的收益是「当面扫码那一份的暴露窗口更短」，
而**真正的保护本来就不是 TTL**：

- 一次性消费（CAS `Pending → Consumed`）—— 用过即废，窗口再长也只能用一次
- 验签 —— capability 不对、字段被改都进不来
- 主动撤销（D3）—— 用户随时能关掉
- 只存 `sha256(capability)`（D4）—— 库被读也拿不到明文

TTL 只是最后的兜底。为了兜底参数从 5 分钟变 24 小时，去换四处分支，不划算。

近场场景用 24h TTL 损失的是什么？只有「扫完码忘了撤销，邀请在表里多躺一天」——
而这恰好是 D3 那个列表要解决的问题，不需要靠 TTL 解。

## D2：端口位置与 CAS 的权威点

```
crates/invite        InviteStore trait 定义（仍 wasm-clean —— trait 不带实现）
   ├── native  →  crates/storage-sql   SeaORM + 新表 + migration
   └── wasm    →  crates/web           IndexedDB 写穿（照 store.rs 的路子）
```

与 `transfer` 的 `SessionStore` / `InboxStore` 完全同构（`crates/transfer/src/store.rs`），
不是新模式。`crates/invite` 的 wasm-clean 硬约束不破：trait 定义不引入任何存储依赖。

wasm 侧照抄 `crates/web/src/store.rs` 的两条经验：`std::sync::Mutex` 在单线程 wasm 下等价
无锁、满足端口的 `Send + Sync`；IndexedDB 的 `JsFuture` 是 `!Send`，用 `SendWrapper` 裹住以
满足 `#[async_trait]` 的 Send 约束（`storage-abstraction.md` 有完整记录，跨线程 panic 在
单线程 wasm 下永不触发）。

**CAS 的权威点仍在内存表。** 一次性语义靠单锁内的检查-置换完成 —— 这是现在
`try_consume` 的核心不变量（「两台设备同时扫同一码时恰有一台成功」），不能因为加了落盘
就变成「先查库再写库」的两段式，那会开出并发双花的窗口。

所以顺序是：**内存 CAS 成功 → 再写穿落盘**。启动时从库全量读回内存表（同 `store.rs` 的
`load`）。落盘失败**不回滚**内存态。

### 修正（实施后审查）：光「不回滚」不够，写穿失败必须能被看见

原文这样论证不回滚：「内存说 Consumed 库还是 Pending，重启后那份邀请会『复活』一次，
但它仍要过验签和 TTL，且用户能在列表里看到并撤销；反过来『库说 Consumed 内存说 Pending』
才会导致双花」。审查用探针实测推翻了其中两点：

1. **「用户能看到并撤销」不成立。** 写穿失败时库里是 `Pending`，重启后列表把它显示成
   「等待对方使用」—— 用户看不到任何被消费过的痕迹，也就不会想到去撤销。**唯一的补救
   信号恰好在这个失败模式下消失了。**
2. **对比项是稻草人。** 回滚不会产生「库 Consumed / 内存 Pending」，它产生的是两边都
   Pending（一致）—— 后果是这份邀请当下就能被再消费一次，而此时配对已经成功了。
   所以不回滚确实更好，但原文给出的理由描述了一个没人会实现的方案。

真正的问题是**第三个选项没被考虑**：端口方法返回 `()`，于是注册表根本不知道写失败了 ——
既不能记指名分歧的日志，也不能标脏、重试或收手。两条 fail-open（消费复活、撤销失效）
全都是静默的。已改成：

- **写方法返回 `bool`**（`upsert` / `remove`）。用 bool 而非 Result 是因为端口层没有统一
  错误类型，而调用方只需要「成没成」这一位；错误详情归实现层日志。
- **`try_consume` 写穿失败即 fail-closed**（新拒绝原因 `NotPersisted`）。能这么做是因为
  调用点的顺序：`respond_pairing_request` 里 `try_consume` 排在 `responder.send(Success)`
  **之前**，所以此刻配对还没成功，报失败是诚实的 —— `store.rs` 原先担心的「配对已经成功
  了却因为写库失败而告诉用户失败」在这个方法上不成立。代价是极少数情况下用户要重新生成
  一条邀请。
- **`revoke` 返回是否落盘**，一路传到 UI：撤销没落盘时要告诉用户「重启后可能恢复」，
  而不是让他以为撤销成功了。
- **`load` 状态单调**：已在内存里推进到终态的条目不会被库里的 `Pending` 盖回去。
  正常路径下不可达（只在全新注册表上调一次），但那是个未被强制的约定，而写穿失败恰好
  会造成「内存 Consumed / 库 Pending」，此时重复 load 就让已消费的邀请复活了。

三条对应的测试都补了（写穿窗口的中间态、消费写穿失败、撤销写穿失败、load 不降级），
测试桩支持挂起与失败注入 —— 原来的 `TestStore::upsert` 立刻完成，那个窗口在测试里
根本不存在。

## D3：撤销列表是必需配套，不是可选增强

24h 把 capability 的存活窗口拉长 48 倍。没有可见性与撤销，用户对「我现在有几个有效邀请在
外面飘」完全没有感知 —— 这在信任凭证上是不可接受的。

所以本 change 的交付里，「已发出邀请列表 + 主动撤销」和 TTL/落盘是同一件事的两半，
不许拆到后续 change。

`revoke_invite` 后端已存在（`src-tauri/src/commands/pairing.rs:95`、
`crates/web/src/node.rs:332`，且是幂等的 —— 不认识的串 no-op），本期是补：

- 一个「列出未过期未消费邀请」的查询（注册表 + 命令 + wasm 导出）
- 三端 UI：列表（创建时间、剩余有效期、可选的备注/去向）+ 撤销按钮
- 倒计时文案从固定「5 分钟」改成相对时间（「23 小时后失效」）

## D4：只存哈希的不变量在落盘后更要守

现在 `InviteRegistry::register` 的注释写着「以 capability 哈希为键，明文不进本表/日志/持久化」。
落盘后这条从「内存里的自觉」变成**磁盘上的硬约束**：

- 表里存 `sha256(capability)`，**永不存明文**
- 邀请全串（含 capability）也不存 —— 需要展示时由 UI 侧持有生成那一刻的字符串，
  重启后列表只能显示元数据（创建时间 / 有效期 / 状态），**显示不出原始链接**
- 这意味着「重启后重新复制那条链接」做不到。可接受：邀请是一次性凭证，重启后想再分享，
  生成一条新的即可（并撤销旧的）
- 日志里也不许出现 capability 明文或邀请全串 —— 落盘路径新增的 tracing 要照这条审

## D5：过期清理

`prune_expired` 现在是 lazy 调用（谁想起来谁调）。落盘后表会无限增长，所以：

- 启动 `load` 时清一次（顺带把过期条目从内存表和库里一起删）
- `register` 时顺手 prune（保持现有 lazy 语义，成本可忽略）
- 清理**只按 `expires_at`，不看状态**：已消费但未过期的记录留着

### 修正（实施中）：保留 `Consumed` 是 UX 需要，不是安全需要

本节原先写的是「已消费的条目不能立即删，否则『一次性』在重启后失效 —— 库里没这条，
重启后同一邀请又能消费一次」。**这个推理是错的**，读代码时发现：

```rust
// InviteRegistry::try_consume / check
let entry = invites.get(&capability_hash(capability))
    .ok_or(InviteRejectReason::Unknown)?;   // ← 查不到 = 拒绝
```

注册表是 **fail-closed** 的：查不到直接返回 `Unknown` 并拒绝配对。所以删掉记录只会让邀请
变成「不认识」，不会放行。删早了不产生双花。

保留 `Consumed` 到过期的真实理由是 **UX**：让发起方在邀请列表里看到「这条已被使用」，
而不是让它从列表里凭空消失（用户会以为自己记错了）。

这个区别值得写下来，因为它决定了**万一将来要优化表大小该怎么权衡** —— 可以牺牲那条
状态显示，但不能反过来以为它在守安全。
