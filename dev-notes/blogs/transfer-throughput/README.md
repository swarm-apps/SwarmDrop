# transfer-throughput — 一次真机实测，推翻三个「合理」的结论

> 2026-08-10。v0.15.2 刚发完版，三台设备跑了一天传输，导出五份日志。
>
> 这五份日志推翻了上一轮诊断的主结论，挖出一个藏在依赖库行为里的 O(n²)，
> 撞见一处「同一台手机走两条协议差 30 倍」的分裂，最后暴露出整个数据面
> **从设计上就不可能跑满带宽**——而修它的过程里，一个 async 组合子的选择又
> 差点重新打开一扇早就焊死的门。

## 这个系列想讲的一件事

**排除法永远弱于正向证据。**

上一轮诊断做得很认真：七个维度并行侦察、三十条候选逐条对抗性验证、推翻其中十条。
结论是「Rust 代码里不存在量级足够的 O(已完成)/块 机制，主根因在代码之外——接收设备的
物理侧（闪存 pSLC 耗尽、SoC 热节流）」。

**它错了。** 而且错得很体面：每一条排除都成立，加总也确实小于 0.1%。问题在于「我没找到」
和「它不存在」之间那道永远跨不过去的沟。

真正定案靠的是一个二十行的耗时探针，和一台散热无忧的桌面机当对照组。

## 建议读法

00 是全系列的方法论底座，**先读**。01–03 是三个彼此独立的根因，可以任意顺序。
04 依赖 03（它讲的是 03 那次改动引入的回归），务必在 03 之后。
05 是 03 的另一半（同一个结构性问题的另一端）+ 一条测试方法，读完 03 再读。

如果你只想带走一件事：**读 00**。剩下四篇都是它那条方法论的实例。

## 一份诚实的免责声明

02 的结论**尚未定案**——那条链路上同时还差着一个未分离的变量。03 的收益是按实测数据
推算的，**没有经过真机验证**；05 同样如此（它的天花板 `proof` 占多大至今没量过）。
这几处在正文里都标了出来，没有藏。

把未验证的推论写成结论，正是 00 那篇要讲的错误。这个系列不打算在批评它的同时再犯一次。
