# 05 · 另一半：怎么给「流水线」写一条会红的测试

> 2026-08-12。03 那篇把接收端拆成了两条并发路径，拿回 50%。
> 两天后的真机数据说，发送端还欠着同一笔账。
> 而修它的时候撞上一个更有意思的问题：**流水线化之后，输出的字节一模一样。
> 那要怎么写一条「改回串行就会红」的测试？**

## 数据先行

局域网直连，Android ↔ 桌面 Chrome，2 GB 单文件，走 WebTransport：

| 方向 | 吞吐 |
|---|---|
| 手机 → 浏览器 | ~20 MB/s |
| 浏览器 → 手机 | ~9 MB/s |

20 那个数落进了 native↔native QUIC 的区间（12–23 MB/s）——**浏览器在接收方向上已经不是
瓶颈了**。这本身是个好消息，也让 2.2 倍的方向差异变得刺眼：同一条链路、同一个传输、
同一台手机，只是换了个方向。

## 两个死掉的假设

**假设一：9 是「传输 + 准备」的合成速率。** 算术上太合了——20 ÷ 2.2 ≈ 9，而浏览器发送
前要先流式读一遍源文件建 outboard。写进笔记之后才去翻代码：Web 端把 prepare 作为**独立
阶段**追踪（`activePrepare` / `bytesHashed`，由 `PrepareProgressEvent` 驱动），传输速率
另算。9 就是数据面速率。假设作废。

**假设二：发送路径独有一份跨 JS↔wasm 拷贝。** 我甚至已经把这句写进了笔记。它是错的：
两个方向都跨两次边界——收是「读帧 + 写 OPFS」，发是「读 File + 写流」。拷贝次数**对称**。

第二个假设特别值得留个记号，因为它会把优化引向完全错误的方向：照着「减少拷贝」去改，
你会在 `Vec` 与 `Uint8Array` 之间来回折腾，而 256 KiB 的 memcpy 是 ~10 µs，
相对 29 ms 的每块预算根本不在同一个数量级。

## 真正的不对称：重叠，不是拷贝

翻两边的代码，形状差别在第一眼就摆着：

```
接收端：收帧循环  ‖  消化循环          （有界队列，join）
发送端：read → proof → write → 下一块  （一条链，从头串到尾）
```

03 那轮流水线化**只动了接收端**。发送端的 `write_block` 从来就是
`read_source_chunk().await → encode_proof() → write_frame().await`。

串行本身是**两端都有**的。但它的代价只在浏览器那侧显形：

- **Android 发**：「读 + 算」是原生文件读（~GB/s）加 NEON blake3。相对 20 MB/s 的网络
  几乎免费，串不串行看不出来。
- **浏览器发**：「读」是 `File.slice().array_buffer()` 的 promise 往返，「算」是 wasm 里
  没有 SIMD 的 blake3。**这段时间完全不与网络写重叠。**

这就解释了「为什么偏偏是浏览器发送慢」——不需要引入任何浏览器特有的机制，
同一条串行链在两端的代价不同而已。

## 一个必须说清楚的天花板

修法是显然的：镜像接收端，拆成**备块 ‖ 发帧**两条路径 + 有界队列 + `join`。

但收益有个硬上限，值得先说清楚，因为它决定了要不要接着做下一步。

`join` 给的是**并发不是并行**，而 wasm 是单线程。真正能重叠的只有「已经交出去、
在我们线程之外跑的事」：

| 阶段 | 在哪跑 | 能与我们的 CPU 重叠吗 |
|---|---|---|
| `read`（`File.slice().array_buffer()`） | 浏览器线程池 | ✅ |
| `write`（WebTransport 写流） | 浏览器网络栈 | ✅ |
| `proof`（blake3 + 拼 bao 切片） | **wasm 主线程，同步** | ❌ |

每块壁钟从 `read + proof + write` 降到约 `proof + max(read, write)`。
**`proof` 是天花板，谁也压不住它。** 如果实测下来 proof 占了大头，这次改动几乎白做，
该动的是别的地方（`+simd128`，或者别每块重算一遍叶子哈希）。

所以这次改动同时是**一次测量能力的升级**：探针从一条拆成两条，
`send`（read/proof/enqueue）与 `send-frame`（queue/write/ack/rest）。
改完之后日志能直接回答「流水线满没满」，而改之前只能推。

## 于是：怎么测「它真的是并发的」？

这才是这篇真正想讲的。

流水线化前后，**流上的字节完全一样**：同样的 Hello、同样顺序的 BlockData、同样位置的
Window、同样的 Finish。所有既有断言——窗口边界、帧计数、错误归因——串行实现全都能过。
换句话说，如果半年后有人为了「简化」把两条循环合回一条，CI 会全绿，
而浏览器发送慢一倍。**「慢一倍」在 CI 里没有任何形状。**

那条断言最后是这么写的：**造一个把写按住不放的对端，直到源文件被读过第二次。**

```rust
// 一次读都还没发生 = 还在写 Hello，放行；否则等门开。
let reads = self.gate.reads();
if reads > 0 && reads < self.open_at {
    self.gate.park(cx);
    return Poll::Pending;
}
```

- **串行实现在这里必然死锁**：它要等当前块写完才会去读下一块，而写正在等下一次读。
- **流水线实现会把门推开**：写挂起期间 `join` 转去 poll 备块循环，它读第二块、
  门开、写继续。

失败形态是超时，而不是断言不等——这正合适，因为「读没跑在写前面」本来就没有一个
可以直接观察的瞬时状态，只有一个可以构造的**死锁**。

顺带一提：这条测试自己也要防假绿。把门槛调到永远够不着（`open_at = 50`，
而全程只有 4 次读），它必须变红——不然说明那道门根本没拦住任何东西。这一步真的跑了一遍。

## 一个被否掉的更简单方案

不要队列、不要两条循环，就在原循环里 `join(备下一块, 发当前块)` —— 经典双缓冲。
行数更少，取消更简单，没有「两条 result 谁先抛」的规则，
稳态重叠效果与深度 1 的队列**完全相同**。

否掉它的理由只有一条：**它把 `read` 和 `proof` 关进同一个 future，探针再也分不开这两段。**
而「`proof` 是不是天花板」正是唯一还悬着的问题。

为省二十行代码，换掉你唯一能拿到答案的那个仪器——这笔账在 00 那篇里已经算过一次了。

## 三条顺手落下的判据

拆完之后有三处「本来就该这样」的东西自己塌了下来，记在这里：

1. **队列深度的判据与接收端不同。** 接收端取满一个窗口是硬要求（队列装得下整窗，
   收帧循环才能立即回 `Window` 放行下一窗）。发送端的窗口节奏由本端的 pacer 决定、
   **不经队列**，所以深度只需要盖住抖动，取 2。抄一个 16 过来会白白多占 4 MiB，
   而且会让下一个人以为那个数是有依据的。

2. **`Finish` 只能在两条路径都成功之后写。** 备块端失败会让发帧端「正常」收敛
   （队列关了），如果发帧循环自己写 Finish，对端就会在只收到一半的时候被告知完成。
   这条也有一条测试看着。

3. **发帧端的错误先抛。** 备块端失败时发帧端只看到「队列关了」，发帧端失败时备块端
   只看到「发帧端已退出」——先抛发帧端，两种情形都落在真因上。
   这和 03 那边「消化端先抛」是同一条规则的两次应用：**抛那条不是在观察对方退场的。**
