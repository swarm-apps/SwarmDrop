# 解耦成了负债：把 bao chunk group 从 16 KiB 拧回 256 KiB

> [01](01-bao-tree-per-chunk-verify.md) 第三节论证了「为什么把验证粒度拧在 16 KiB」，
> 其中一条理由是：传输块 256 KiB 恰好是它的整数倍，于是**验证粒度与传输粒度彻底解耦、
> 互不干扰**。那条推理没有算错，只是把一个从来没有消费方的性质当成了优点。
>
> 2026-08，chunk group 改成 `CHUNK_SIZE`（256 KiB）——每个传输块恰好一个叶子。
> 这篇讲那条「优点」是怎么变成负债的，以及为什么发现它花了这么久。

## 一、当初的推理，逐条复核

01 那张表是对的：

| chunk group | outboard / 文件 | 最小可验单元 |
|---|---|---|
| 1 KiB | 6.25% | 1 KiB |
| 16 KiB | 0.39% | 16 KiB |
| 256 KiB | 0.024% | 256 KiB |

「拧太小 outboard 膨胀、拧太大验证粒度变粗」也没错。问题出在**怎么给「验证粒度变粗」
标价**。

当时的话是：「接收端必须先把一整个 group 缓冲齐才能验、才能拒，『坏块当场发现』的即时性
被拖钝。」——这句话在通用场景里成立。但在本仓，有一个当时没被问出口的问题：

> **谁会请求一个比传输块更细的验证？**

答案是：没有人。数据面的最小传输单位就是 `CHUNK_SIZE` = 256 KiB，`fetch_plan` 的 offset
恒是它的倍数，`encode_proof` 每次收到的 `block` 也就是一个传输块。接收端**永远**是拿到
完整的 256 KiB 才调 `decode_and_verify`。16 KiB 的验证能力从落地那天起就没被行使过一次。

于是「解耦」的真实含义变成了：**为一件不会发生的事，每个文件多付 16 倍的成本。**

## 二、那 16 倍付在哪里——不是体积，是调用次数

体积这一项其实好办：0.39% 对 0.024%，1 GiB 文件是 4 MiB 对 256 KiB。存起来当然有差别，
但没人会为这个改 wire。

真正的代价藏在**构建 outboard 时对宿主的调用次数**上。bao 按 chunk group 粒度向底层
reader 要数据，而本仓三端的 `read_source_chunk` 都是**每次调用重新打开文件**：

| 端 | 单次调用的固定开销 |
|---|---|
| 桌面 | `File::open` + `seek`，整个包在 `spawn_blocking` 里（还有一次线程池调度） |
| 移动 | JSI 往返 + `new File(uri).open()` → seek → read → close，**句柄刻意不缓存** |
| 移动（Android SAF 源） | 上面那些 + 每次一趟 `ContentResolver.openFileDescriptor()` binder IPC 到 DocumentsProvider |
| Web | `File.slice().arrayBuffer()`，每次一个 Promise + 一次结构化拷贝 |

字节总量不变，但**调用次数差 16 倍**。100 MiB 的文件，16 KiB 粒度是 6400 次，256 KiB
粒度是 400 次。Android 上转发一个刚收到的 100 MB 视频（落点治本之后接收区恒为 SAF tree，
条目路径就是 `content://`），那就是 6400 次 binder IPC 对 400 次。

这个成本在设计时不可见，因为它不在 bao 这一侧，也不在传输这一侧——它在**宿主端口的实现
细节**里。而端口的契约（「精确返回 `[offset, offset+length)`」）对调用频率一个字都没说。

## 三、发现它的路径：从一个 UI 症状开始

没有人是冲着 chunk group 去的。起点是一个用户能看见的现象：**点了发送之后，进度条走完
100% 还要再等一段，期间界面上一个可交互元素都不剩。**

顺着查下去是这样一条链：

1. 进度事件全部产自 `prepare` 的第一遍读（扁平 BLAKE3 算 checksum）；
2. 第二遍读（建 outboard）**一个事件都不发**——所以进度条走完了，活还没干完；
3. 那两遍读本可以合并，因为 `build_outboard_from_source` 返回的 root **就是** checksum
   （01 里那条「白拿的不变量」）；
4. 要合并，进度 emit 就得挂到 bao 那遍的 reader 上；
5. 挂上之后才发现：那遍的读粒度是 16 KiB，比另一遍细 16 倍——**删掉的那遍其实是便宜的
   那遍**。

第 5 步是转折点。原本以为「合并两遍读」能省一半时间，一算调用次数才知道只省了 6%
（400 / 6800）。真正的大头一直是那个从没被行使过的 16 KiB 粒度。

一度设计过一层「256 KiB 顺序合并缓冲」把 bao 的 16 KiB 请求攒起来。写到一半意识到：
**如果 chunk group 本来就是 256 KiB，这层缓冲根本不需要存在。** 那层缓冲要处理非顺序
读的 fallback、要处理 EOF 附近的短读、要让长度校验判据从 `!= len` 变成
`!= len.min(size - offset)`——全都是为了绕开一个自找的问题。

删掉它比写好它容易。

## 四、代价：这是一次 wire 破坏

chunk group 决定树的形状，树的形状决定 proof 的字节。16 KiB 端产出的 proof 喂进
256 KiB 端的 `decode_ranges`，**第一个块**就 `ParentHashMismatch` → 协议违规 → 断流 →
Interrupted 无限重试。

本仓对这类破坏有写死的体例，就在 `protocol.rs` 那段血泪注释里——它讲的是 `/2` → `/3`
（新增流控窗口帧）：

> 加一个帧 tag 就必须换协议名，因为解码器对未知 tag 是**硬失败**……若沿用 `/2`，
> v0.12.1 的发送端会在第一个窗口边界（4 MiB）静默打断每一个 v0.12.0 接收端。

chunk group 变更属于同一类，而且**更严重**：那个至少要等到 4 MiB 边界，这个第一个块就断。
所以协议名从 `/3` bump 到 `/4`。

有意思的是随之而来的第二个决定：`/2` 与 `/3` 的注册被**整体摘除**了。

先说清楚代价，因为它容易被「反正没人用」糊弄过去：SwarmHive 上 v0.12.1 到 v0.14.0（含
移动端）都已发布，摘除意味着那些客户端与新版**双向都传不了**。做这个决定是因为当时用户
基数小到不值得为兼容付代价，不是因为不存在存量。

而摘除本身不是因为「不用兼容所以懒得留」——恰恰相反：

> **留着旧协议名却让它跑新的树形状，等于把「版本不匹配」伪装成「传输老是断」。**

摘掉之后，旧端拨过来得到的是一次 `UnsupportedProtocol`——协商阶段的响亮失败。
**bump 协议名的全部价值，就是把不兼容前移到协商阶段。** 「不考虑兼容性」从来不等于
「不用 bump」。

### 但「响亮」不是自动的

这里有个当时差点漏掉的半步。`UnsupportedProtocol` 拿到之后，代码把它和拨号超时一样压成了
一句 `AppError::Transfer(String)`，于是版本不兼容走 `Interrupted` → suspended/**recoverable**
——续传机器拿同一个协议名一次次重试。**协商阶段确实响亮地失败了，但那份信息在函数内部就
被字符串化了，没有任何消费者能据此分支**，用户看到的仍然是「传输老是断」。

也就是说，上一节论证的全部价值在落地时是假的，直到给它一个真正的判别码
（`FailureCode::PeerProtocolUnsupported`）并让三端渲染成「对方版本太旧，请让对方升级」。
**分类没做完，bump 就只是换了个字符串。**

还有反方向补不了的那一半：旧发送端只会拨 `/3` 和 `/2`，两个都被拒之后它按自己那一版的
逻辑走无限重试——那一版的代码已经发出去了。新端能做的只有在自己这侧把话说清楚，外加
在推终态之前经**控制面**（那个协议名没变，旧端认得）发一帧 Cancel，免得对端一直挂在
「已接受、等着数据面连进来」的状态上——接收侧只有启动时才回收过期会话，不发这一帧它
能挂到下次重启。

## 五、一条安静的、永久的失败：存量 outboard

outboard 会落库（`transfer_files.outboard` BLOB）供续传免重算。chunk group 一变，那些
字节就作废了——但它们**非空，而且看起来完全合法**。

而当时的失效判据是：

```rust
if pf.outboard.is_empty() && pf.size > 0 { /* 重算并回存 */ }
```

一份 16 KiB 时代的 BLOB 非空，于是被原样载入、当成 256 KiB 树用、每次 `encode_proof` 都
`ParentHashMismatch`，而重算分支**永远不触发**。不 panic、不报错、日志里只有一句「bao
encode 失败」。那条中断的发送会话就此**永久**续不上传。

修法不是加一条迁移（那只治当下这一次），而是把判据换成长度：

```rust
if !bao::is_outboard_usable(&pf.outboard, pf.size) { /* 重算并回存 */ }
```

`outboard_len(size)` 是 `(blocks - 1) * 64` 的确定性函数，**长度本身就是格式版本号**。
将来再调 chunk group 也不需要写迁移。它还顺手修掉一处既有浪费：新粒度下
≤ 256 KiB 的文件 outboard 恒为空且**合法**，旧判据会把它们全判成缺失，于是每次续传都白读
一遍整文件再存回一个空 vec。

## 六、留下的三条

**1. 「解耦」不是免费的形容词。** 两个粒度解耦意味着它们可以独立变化——但只有在真的会
独立变化时才值钱。本仓从头到尾只有一个传输粒度，解耦买的是一个永远不会行使的期权，
保费按 16 倍收。

**2. 成本可能不在你正在看的那一层。** chunk group 是 bao 的参数，代价却落在宿主端口的
实现里。选参数时手上那张表（outboard 占比 vs 最小可验单元）两列都对，只是**少了一列**：
「构建时对宿主的调用次数」。

**3. 验证粒度是单向门。** 256 KiB 现在是最小可独立验证单元。将来若要做 range 请求、
部分文件预览、或与 iroh-blobs 互通，它就是硬下限。这条记进了 `net-kernel.md` 的已知负债
——不是因为现在有问题，而是因为将来发现有问题时，得有人知道这是一次有意的选择。
