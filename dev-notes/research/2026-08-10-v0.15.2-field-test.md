## 3. 新发现 A：接收侧验签是 O(n²)

### 3.1 判别实验

上一份诊断的主假说是「接收设备物理侧」（闪存 pSLC 耗尽 / SoC 热节流）。桌面接收侧是
天然对照组——散热无忧、NVMe 无 pSLC 耗尽问题。两边逐窗口（每窗口 = 256 块 = 64 MiB）
的阶段耗时：

**移动端接收（`8e81035d`，桌面→移动）**

| 累计块 | MB/s | wait | **verify** | write | ckpt | rest |
|---|---|---|---|---|---|---|
| 512 | 17.98 | 2687 | **168** | 297 | 378 | 26 |
| 15616 | 14.62 | 3084 | **461** | 350 | 447 | 32 |
| 28416 | 10.68 | 4386 | **765** | 366 | 420 | 52 |

**桌面接收（`961da207`，移动→桌面）— 对照组**

| 累计块 | MB/s | wait | **verify** | write | ckpt | rest |
|---|---|---|---|---|---|---|
| 512 | 42.93 | 1234 | **13** | 34 | 207 | 0 |
| 15616 | 25.42 | 2068 | **89** | 36 | 321 | 1 |
| 28416 | 16.19 | 3415 | **247** | 35 | 251 | 1 |

三条读数：

1. **桌面也劣化了**（42.93 → 16.19 MB/s），而且 `verify` 增长得比移动端更凶
   （**×19** vs ×4.6）。→ **热节流与闪存假说双双推翻**。
2. **`write` 全程恒定**（桌面 34→35，移动 297→366）。这一段才是真正的闪存写入。
   闪存若在劣化，它必须先动——它没动。
3. **`verify` 是唯一显著随进度增长的本机工作**，`ckpt` / `rest` 均无趋势。

### 3.2 发送侧的对称对照

同一台移动端**做发送方**时，`proof`（生成 bao 证明，同样是 CPU + 同一棵树）：

| 累计块 | proof |
|---|---|
| 512 | 122 ms |
| 28416 | 155 ms |

**×1.27，基本恒定。** 验签涨 19 倍而生成证明不涨——这排除了「blake3 或树深度」这类
两侧共有的因素，把问题锁死在**接收侧独有的那段代码**。

### 3.3 根因

`crates/transfer/src/bao.rs:344-348`，`decode_and_verify` 每块新建 outboard 写入目标：

```rust
let mut outboard = PreOrderOutboard {
    root,
    tree,
    data: Vec::<u8>::new(),   // ← 每块一个新的空 Vec
};
```

它与两处依赖行为组合成了 O(n)：

1. `bao_tree` 的 `PreOrderOutboard::save`（`io/sync.rs:156-168`）把每个 parent 写到
   `tree.pre_order_offset(node) * 64` —— 偏移量随节点在树中的位置增长。
2. `positioned_io` 的 `WriteAt for Vec<u8>`（`src/vec.rs:22-25`）：

```rust
// Resize the vector so pos <= self.len().
if pos >= self.len() {
    self.resize(pos, 0);      // ← 零填充到 pos
}
```

于是**每验证一块，都要把一个空 Vec 零填充到该块祖先链的最深偏移处**。7.49 GiB 文件的
outboard 全长 = (30690 − 1) × 64 B ≈ **1.87 MiB**，末段每块都在做这件事，且 `resize`
过程中还要经历多次 realloc 拷贝。

代价与实测吻合：桌面末段 `247 ms / 256 块 ≈ 0.96 ms/块`，移动端 `765 / 256 ≈ 2.99 ms/块`
——正是零填充 ~1.87 MiB 在两类设备上的量级。

**发送侧为什么不受影响**：`encode_proof` 用的是
`PostOrderOutboard { data: outboard_bytes }`，一个**只读 `&[u8]`**（`bao.rs:308-312`），
预先就是完整长度，永远不需要扩展。这正是 §3.2 那组对照数字的机制解释。

### 3.4 修复方向

代码注释本身已经写明「decode 写进去的 parents **用完即弃**」（`bao.rs:342-343`）。既然
用完即弃，就不该真的把它们写进一块随位置增长的内存：

- **首选**：换成一个丢弃写入的 sink，O(n) → O(1)，改动约 15 行。

  **前提已验证，风险为零**——`decode_ranges`（`io/sync.rs:505-528`）的循环体只有两支：
  `Parent => outboard.save(...)`、`Leaf => target.write_all_at(...)`，**全程不调
  `outboard.load()`**。验签在 `DecodeResponseIter` 内部靠 `outboard.root()` 独立完成，
  `save` 进去的 parent 从来没有被读回过——对不做再分发的接收端，它纯属浪费。

  实现要点：`decode_ranges` 要求 `O: OutboardMut + Outboard`，而这两个 trait 对
  `PreOrderOutboard<T>` 分别要 `T: WriteAt` 和 `T: ReadAt`，所以 sink 需同时实现两者。
  `read_at` 返回 `Ok(0)` 即可——万一将来 bao-tree 改成会 `load`，它会以
  `UnexpectedEof` **硬失败**（验签 `Err`，立即被测试和真机抓到），不会静默算错。

- **退路**（若上面因将来的库行为变更不可用）：在接收 actor 里持有一个跨块复用的 buffer，
  一次性 `vec![0u8; outboard_size]`，每块 `mem::take` 进出。O(1) 摊销，但要常驻
  outboard 全长的内存。

### 3.5 这条能解释多少？

**必须说清楚：它是已确证的算法缺陷，但量级不足以解释全部劣化。**

以桌面接收侧末段为例，总窗口耗时从 ~1.49 s 涨到 ~3.95 s（+2.46 s），而 `verify` 只贡献
+0.23 s（约 **12%**）。剩下的增量落在 `wait`（1234 → 3415 ms）与对端的 `ack`
（1395 → 3288 ms）——**两边都在等对方**，这是 `WINDOW_CHUNKS = 16`（4 MiB 停等窗口）
的镜像表现，探针覆盖不到窗口之外的链路时间。

有一条合理但**未经证实**的放大链条：接收侧验签变慢 → 从流里读得慢 → 传输层接收窗口
收缩 → 发送侧被流控压制得比应用层多慢的那点更厉害。修完 A 之后重测一次即可判定：
若吞吐恢复平坦，链条成立；若仍劣化，说明另有独立成因（那时 `verify` 已被排除，
搜索空间显著变小）。

## 4. 新发现 B：移动 ↔ Web 只有 0.36 MB/s

### 4.1 定位

**已确认是局域网直连，不是 relay**：Web 端日志有
`webrtc hole punching succeeded peer=12D3KooWFpU2…`（移动端），三端都在 `192.168.1.0/24`。

| 侧 | 阶段分解 |
|---|---|
| 移动（send） | read=0% proof=0% **write=43%** **ack=55%** |
| Web（recv） | **wait=99%** verify=0% write=0% ckpt=0% |

Web 侧全部 CPU 工作合计 **4 秒 / 644 秒 = 0.6%** —— 接收端不是瓶颈，它在饿着。

决定性对比是**同一台移动端做发送方**的 `write`（把帧写进流，含传输层背压）：

| 目标 | write 每块 |
|---|---|
| → 桌面（QUIC / webrtc-direct） | **0.054 ms** |
| → Web（WebRTC 打洞） | **296 ms** |

**5500 倍。** 瓶颈完全在 `write_frame` 下游的 WebRTC 打洞数据面。

顺带：`ack` 为 6140 ms/窗口，而对端消化只要 ~4 s/全程，所以 `ack` 也几乎全是链路时间，
与 `write` 指向同一处。

### 4.2 与新发现 A 无关

该会话仅 927 块，outboard 全长 ≈ 58 KiB，A 的零填充代价可以忽略（Web 侧
`verify` 实测 2.0 ms/块且无增长趋势）。**两条是独立问题。**

### 4.3 未定的根因

局域网内 WebRTC datachannel 跑 0.36 MB/s（≈2.9 Mbps）显著偏低，正常应有数十 Mbps。
候选（均未验证）：SCTP 拥塞/接收窗口参数、每帧一次事件循环往返的分片开销
（296 ms / 256 KiB ≈ 18.5 ms per 16 KiB 帧，很接近「每帧一个 JS tick」的量级）、
打洞后 ICE 选中的候选对不是最优路径。

判别建议：先在同一条打洞链路上跑一次**桌面→Web**。若同样是 0.36 MB/s，问题在
Web(wasm) 侧的读路径；若桌面→Web 正常，问题在移动端 native 的写路径。

## 4.5 补测（UTC 12:23–12:58）：反向也测了，并揪出一条构造性 bug

第二批日志（`swarmdrop-mobile` + `swarmdrop-web-1786367854423`）补上了 Web **发送**方向。
两份 Web 日志是**同一个页面会话**（后者开头就是 `37ff76b6` 的收尾），12:03:55 那条打洞连接
一直复用，所以后段没有新的打洞事件——**链路仍是 webrtc 打洞直连，不是 relay**。

| 会话 | 方向 | 体量 | 耗时 | 吞吐 | 发送侧 `write` |
|---|---|---|---|---|---|
| `37ff76b6` | 移动 → Web | 231.8 MiB | 644 s | 0.36 MB/s | 43%（296 ms/块） |
| `bc020160` | Web → 移动 | 1.99 GiB | **35.4 min** | 0.96 MB/s | **77%**（201 ms/块） |

**两个方向对称地卡在 ~1.2 MB/s 的 SCTP 排空速率上**，而两侧的应用层工作都恒定且可忽略
（Web 发送侧 `read` 340 ms / `proof` 520 ms 每 256 块全程不变；移动接收侧 `wait` 95%）。
逐窗口吞吐在 0.68–1.96 MB/s 之间**剧烈波动而非单调劣化**——链路特征，不是算法特征。
方向对称这一条尤其重要：两侧是两套不同的 SCTP 实现（浏览器 vs webrtc-rs），**都是这个量级**，
所以瓶颈不在任一端的实现里。

### 构造上不可能成功的 relay 预约（真 bug）

Web 端在**整个 35 分钟传输期间**，持续向 `12D3KooWFpU2gSYz`——**正是它同时在传 2 GiB 的那个
移动端**——请求 relay reservation，地址是：

```
/ip4/192.168.1.98/tcp/45885/p2p/12D3KooWFpU2…/p2p-circuit
```

**`/tcp/`。浏览器拨不了 TCP。** 所以这不是"运气不好"，是永远不可能成功：重试计数从 0 单调
爬到 **23 轮且从不重置**（移动端同期只到 4 轮就成功了）。`aeb4c80f` 的退避闸门确实在工作
——它让计数累加、不再刷屏——但它治的是症状，没治「候选本身就是废的」。

连带产物：**182 次** `Stream dropped … sending Reset` + **122 次**
`Dropping inbound identify push stream because we are at capacity`，与传输窗口交错出现。

**根因**在 `crates/net/src/actor.rs:1576` 的 `circuit_base`——它刻意不做 transport 白名单，
理由写在注释里：「新传输随时会加，漏一个就是把一条本来能用的基址判死」。这在 native 上成立，
**在 wasm 上不成立**：浏览器的 transport 是**封闭且已知**的集合（webrtc-direct / webrtc），
`/tcp`、`/quic-v1` 在那里永远拨不通。而 `first_circuit_base` 取第一条结构上合格的地址，
移动端的 TCP 地址恰好排在前面。

**修复方向**：候选筛选要多问一句「**本端**能不能拨这条地址」，而不只是「这条地址结构上能不能
当基址」。判据在 wasm 上是硬的（封闭集合），在 native 上可以保持现有的宽松放行。

### 量级上的诚实交代

**stream churn 解释不了 0.96 MB/s。** 182 次 reset 摊到 35 分钟是每 11.5 秒一次，122 次
identify drop 是每 17 秒一次——这个频率吃不掉 77% 的 `write` 阻塞。它是一条独立的、确凿的
缺陷，但**不是**吞吐的主因。

它真正的价值在于：**它是目前最大的干扰变量**。在同一条 WebRTC 连接上持续开关 stream，
会让「SCTP 为什么只有 1.2 MB/s」这个问题没法干净地测。所以顺序应当是**先修它，再测吞吐**——
若修完仍是 ~1 MB/s，搜索空间就干净地缩到 ICE 候选对与 SCTP 参数上（届时需要抓 ICE
selected candidate pair，现有日志没有这项）。

## 5. 观察项（未定级）

1. **OPFS 配额没有预检**（旧版复现，新版未再触发但代码未改）。现在的失败形态是收到一半
   才爆 quota，对端只看到一句「对端中止传输」。应在 accept offer 前用
   `navigator.storage.estimate()` 预检并给出可读拒绝理由。
2. **向已配对 peer 预约 relay 后立刻丢失**。新版仍有一次（11:43:42，accepted 后 3 ms 即
   丢失并重建），Web 端有 6 次小循环。`aeb4c80f` 的退避闸门已阻止它刷屏，但**这个预约
   本身是否有意义**值得问——对端刚刚已经直连成功了。
3. **`CHECKPOINT_INTERVAL = 10`** 让 30690 块的会话写了 3069 次 checkpoint，桌面
   `ckpt` 占 11%、移动占 8%。它不随进度增长（非 A 的一部分），但绝对占比不低。
4. 旧版时段移动端进程重启 **10 次**（新版 4 次，均在测试开始前）。若非人为，值得查
   Android 后台回收。

## 6. 建议的下一步顺序

1. **修 A**（§3.4 首选方案，先验 `decode_ranges` 是否 `load`）。改动小、有双端正向证据、
   影响所有大文件接收。
2. **重测桌面↔移动 7.5 GiB 来回**，读窗口序列：`verify` 是否变平、吞吐是否不再劣化。
   这一步同时判定 §3.5 那条放大链条。
3. **跑一次桌面→Web** 以二分 B 的根因（§4.3）。
4. 上述结论落定后再决定要不要动 `WINDOW_CHUNKS`——在 A 修好前调窗口，只会把一个
   O(n²) 问题的表现挪个位置。
