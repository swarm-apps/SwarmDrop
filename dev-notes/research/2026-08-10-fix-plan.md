## 优先级

### 🔴 A 级 —— 功能不可达 / 丢数据

| # | 问题 | 根因 | 改哪 | 量 |
|---|---|---|---|---|
| **A1** | 移动端收到的文件**发布不出去**，且每次续传都撞同一个坑（死循环，2 GB 暂存永远占着） | `expo-file-system` 的 `forContentURI` 不持有 `ParcelFileDescriptor`，GC finalizer 关掉 fd。**本仓修这条的 pnpm patch 从未进过 Android 构建**——SDK 56 默认吃预编译 AAR | `mobile/package.json` 加 `expo.autolinking.android.buildFromSource: ["expo-file-system"]` | S–M |
| **A2** | 移动端**无法解除配对 / 阻止设备 / 改接收策略** | 设备详情页无滚动容器 + 用错底栏组件（`BottomActionArea` 无背景不吃安全区，而 `BottomActionBar` 两样都有）。展开「链路详情」后触发 | `device/[peerId].tsx` 四处 | S |

**A1 的证据链是闭合的，零推测**：

```
javap -p <expo.modules.filesystem-56.0.8.aar>/…/FileSystemFileHandle.class
  → 无 parcelFileDescriptor 字段、无 describe()
grep parcelFileDescriptor node_modules/expo-file-system/android/.../FileSystemFileHandle.kt
  → :56 有。node_modules 里的源码是打过补丁的
expo-modules-autolinking resolve -p android --json
  → publication={…, repository: local-maven-repo}，shouldUsePublicationScriptPath: None
```

⇒ `shouldUsePublication=true` → `linkProject()` 被跳过 → 编 AAR，patch 从未参与。
旁证：日志里 JS 侧的改动（`→ Caused by`、`（已写 N/M 字节）`）**都在**，Kotlin 侧的 reason 却是裸
`'Bad file descriptor'`（无异常类名，正是上游 `e.message` 的输出）。**JS 生效、Kotlin 不生效，缝就在这。**

> **A1 同时修两条路径**：publish 的写，以及发送侧读源——`foreign-file-access.ts:127` 的
> `new File(sourceId).open()` 在 SAF 源上走同一个 `forContentURI`，
> **每个 256 KiB chunk 泄漏一个 fd**，2 GB 发送开约 8000 个句柄，今天没爆只是运气。
> 它是唯一一条同时进两个优先级的改动，**应当最先合**。

**动手前零成本先验一次**：抓 logcat，未修的构建应看到 CloseGuard 的
`A ParcelFileDescriptor was not closed`。

**B1 是三端共享代码，一次修三端**（桌面很少被杀所以没暴露）。协议本身是对的——

⚠️ B1 修法有个陷阱：**必须数块，不能 `bytes / CHUNK_SIZE`**。floor 版本在「短尾块已收到而中间有洞」

## 本次实测澄清了什么

**① 症状 B（50→7 MB/s 劣化）没有复现。** 两个方向全程平坦（手机 send 14.17–15.58，
手机 recv 9.23–10.38，32 个窗口无趋势）。这**排除了**「传输实现里有 O(已完成) 的算法、
内存/句柄单调增长、bitmap 线性扫描」这一整类猜想——那类东西在 2 GB / 8000 块上一定显形。
剩下的候选只有三类：绑定在**某条特定链路**、绑定在**特定端**（Web/OPFS）、或环境性（热节流）。
**不要销案，但也别盲追**——探针已经有了，在能复现的链路上重跑一次即可判定。

**② 桌面 → 手机的瓶颈是链路带宽，不是代码。** 桌面 send `ack=98%` + 手机 recv `wait=83%`，
两端 CPU/IO 都在打盹。稳定 9.73 MB/s ≈ 78 Mbps。**这个方向再优化两端代码收益为零。**
值得查的是「为什么打洞成功后只有 78 Mbps」。

> 次级发现：手机 recv 的 `ckpt=12838ms/6%`，而 checkpoint 每 10 块才刷一次
> ⇒ **单次落库 15.8 ms**。现在被 `wait` 掩盖，链路提速后会浮出水面。先记一笔，不动
> （`CHECKPOINT_INTERVAL=10` 是「续传最多重拉 9 块」的判据）。

**③ `支路缓冲已满` 零命中不能作为 udp_mux 假设被推翻的证据。** 那条日志只存在于
`/webrtc-direct` 的 **native 监听端 mux**；本次两端走的是 `/webrtc` **打洞**
（日志 05:15:42 `upgrading relayed connection via webrtc hole punch` → 05:15:43 `succeeded`），
根本没实例化那个 mux。**零命中 = 那段代码没跑。** udp_mux 仍是症状 A 的**未排除**候选。

## 编排纪律

**A1 是 native 改动要重建 APK；D1 要重跑 `ubrn build`。不要把它们混进同一个 APK**
——两者都会改吞吐，混在一起下一份探针日志就没法归因了。

建议三次构建：`A1 + A2 + B + C`（一次）→ 重测 → `D1`（一次）→ 重测 → `D2`（一次）。
