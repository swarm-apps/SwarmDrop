# Web 应用区 i18n 选型：Lingui，且不引入 `[lang]` 路由段

> **状态：🟡 已给结论，待实施（2026-08-02）。**
> 对应 issue #102。选型结论是 **Lingui + 运行时切换**，四条关键路径已在 `docs/` 里
> 实测跑通（spike 已清理，未入库）。本文记的是「为什么这么选」与「实施时会撞到什么」。

## 结论先说

| 决策 | 选择 | 一句话理由 |
|---|---|---|
| 库 | **Lingui 5** | 三端同一套 + `.po` 同格式 + macro 在 Next 16 Turbopack 下**实测可用** |
| 多语言组织 | **运行时切换，单份静态产物** | 应用区是工具型 SPA，SEO 无关；不动路由结构就不动 `nav.ts`、basePath、产物数量 |
| 是否用 `[lang]` 路由段 | **不用** | 它技术上可行（locale 不是运行时值，`generateStaticParams` 预生成得出来），但收益只有 SEO，代价是所有链接多一层前缀 |
| 与 fumadocs i18n | **各自为政** | 文档区还没开 i18n；真要开时它有自己的 `[lang]` 机制，与应用区互不干扰 |
| catalog 位置 | `docs/app/app/_locales/{locale}/messages.po` | 不与桌面端共享文件，靠 `sourceLocale: zh` + 术语约定对齐 |

## 实测了什么（这是选型的主要依据）

文档只能告诉你「据说支持」。以下四条在本仓 `docs/`（Next 16.2.6 + Turbopack +
`output: "export"` + `basePath`）实跑过：

| # | 验证项 | 结果 |
|---|---|---|
| 1 | `@lingui/swc-plugin@6.6.0` 编译 `t\`…\`` 与 `<Trans>` | ✅ `✓ Compiled successfully in 5.7s` |
| 2 | 静态导出预渲染 26 个页面 | ✅ 全过 |
| 3 | 产物 HTML 里的插值文案 | ✅ `out/app/settings/index.html` 里是 `探针：设备 {name} 有 {count} 个文件` |
| 4 | `lingui extract` + `lingui compile` | ✅ 提取 2 条 / 三个 locale；compile 出 `messages.js` |

**第 1 条是整个选型的关键**，因为它是唯一有真实风险的一环：Lingui 官方把 SWC plugin 标为
experimental 且声明「`@swc/core` 之间不保证 semver 兼容」，社区也有 Turbopack 下
wasm plugin 崩溃、路径解析失败的报告。实测通过意味着**当前版本组合可用**，但这条依赖
需要在升 Next 时复验——见下面「已知风险」。

一个实测顺带暴露的约束：**没有 `I18nProvider` 时预渲染直接失败**
（`Cannot destructure property 'i18n' ... as it is null`）。静态导出会在 Node 里跑一遍
每个页面，所以 provider 必须在那一刻就能同步给出实例，`i18n.load()` / `i18n.activate()`
不能是异步的。这决定了下面的「预渲染语言」设计。

## 为什么不是别的

### Paraglide（inlang）—— 出局，硬性不兼容

编译成纯函数、零运行时，指标漂亮，但 **`paraglide-next` 明确不支持 `output: "export"`**
（[opral/inlang-paraglide-js#109](https://github.com/opral/inlang-paraglide-js/issues/109)）：
它依赖 middleware 做语言检测与 rewrite、依赖 headers 传语言状态，静态导出两样都没有。

绕开适配器直接用核心库是可以的，但那样就退化成「自己写运行时切换」——省下的正是适配器
的价值，而代价是三端分裂成两套 i18n 心智。

### next-intl —— 出局，同样撞静态导出

生态最热，但标准用法要 middleware 或 `[locale]` 段。前者静态导出不支持，后者见下。
它 2026 年加的 AOT 编译能把运行时压到 ~4kB，但那解决的是体积，不是本仓的约束。

### react-i18next —— 可用但没有理由选

运行时 JSON 加载，静态导出下能跑。但它与桌面端/移动端的 Lingui 分叉：两套 API、两套
提取工具、两种 catalog 格式，而**术语一致性是本项目的明确验收标准**（#102 写着「配对」
「邀请」「收件箱」「传输」等核心名词不能各叫各的）。同一个词在两套工具里维护，漂是迟早的。

### Lingui 但不用 macro —— 备选，不是首选

Lingui 可以不用 macro：手写 `<Trans id="..." message="..." />` 与 `i18n._()`。
这样彻底绕开 SWC plugin 的风险。代价是每条串都要手工起 id，且写法与桌面端分叉
（那边用 macro）。

**留作 SWC plugin 出问题时的退路**：切过去不用换库、不用换 catalog 格式，只改写法。

## 为什么不用 `[lang]` 路由段

先澄清一个容易误引用的约束：`CLAUDE.md` 与 `web-app-frontend.md` 写着「运行时 ID 不能进
路由段」，理由是 sessionId 是运行时 UUID、`generateStaticParams` 预生成不出来。
**locale 不是那种东西**——它是编译期已知的有限集合（zh / zh-TW / en），
`app/[lang]/...` + `generateStaticParams` 完全成立，Lingui 官方的 App Router 教程正是这么做的。

所以这里是**权衡**，不是限制：

| | `[lang]` 段（编译期分语言） | 运行时切换（单份产物） |
|---|---|---|
| SEO | 每语言独立 URL，可被收录 | 三种语言同一 URL |
| 首屏 | 直出目标语言 | 先出源语言，hydrate 后切 |
| 产物 | ×3（26 页 → 78 页） | ×1 |
| `nav.ts` | 所有 href 要带 locale 前缀，叠在 basePath 之上 | 一行不改 |
| 语言记忆 | URL 自带 | 要 localStorage + 一次客户端切换 |

**判据是 SEO 对 `/app` 值不值那些代价。不值**：应用区是登录后即用的工具页，全部内容
（设备、传输、收件箱）都是本机运行时状态，没有任何可被搜索引擎索引的公共内容；它甚至
**必须有 JS 才能工作**（wasm 节点在浏览器里跑）。真正需要 SEO 的是落地页与文档区，
那两块不在本次范围。

反过来，`nav.ts` 那一行代价是实打实的：它是导航的单一事实源，`sendToPeerHref` /
`transferSessionHref` / `inboxItemHref` 都从它派生，再叠一层 locale 前缀会让每个 builder
多一个参数，而 basePath 已经在下面垫了一层。

**首屏闪烁**这条代价是真的，但本仓已经有同类先例与解法：桌面端 `preferences-store` 的
`onRehydrateStorage` 立即应用主题以避免闪烁（记在 `theme-and-styling.md`）。语言同理——
读 localStorage 是同步的，可以在 hydrate 的第一拍就切完。

## 实施要点

### 预渲染语言 = 源 locale（zh）

provider 在模块级同步 `load` + `activate` 源 catalog（实测过，见上）。客户端 hydrate 后
读 localStorage 决定是否 `dynamicActivate` 到别的语言。

⚠️ Lingui 官方提醒「**不要在模块级创建依赖 locale 的字符串**」——那会让预渲染把源语言的
文案烤死进产物、之后切不动。常量文案（如 `nav.ts` 的 `label` / `description`）现在正是
模块级字符串，它们要改成函数或 `msg` 描述符，在渲染时才求值。**这是本次改造面最大的一块。**

### catalog 编译产物是 CJS

`lingui compile` 默认出 `module.exports = {messages: JSON.parse("…")}`。动态
`import()` 它在 Turbopack 下走 interop 可以，但实施时确认一下是否要配成 ESM。

### 不与桌面端共享 catalog 文件

两个独立 pnpm workspace，共享文件要么建第三个包、要么符号链接，都比收益重。
靠三条约定对齐：同一个 `sourceLocale: zh`、同一个 `.po` 格式、核心名词写进术语表。

### `/p/` 落地页单独想办法

`docs/public/p/index.html` 是内联 HTML 无框架的（3.2KB gzip，理由见
`web-app-frontend.md`），不能把 150KB 的 React runtime 拉进去。它的多语言只能内联一份
小字典 + `navigator.language` 判断。**不在 #102 的主路径里，可以后手。**

### 收件箱标题仍会是中文

`crates/transfer/src/inbox.rs::inbox_title` 产出的中文串**直接落库**，前端拿到的是成品
字符串，Lingui 无从下手。见 #110——它不阻塞 #102 开工，但 #102 做完收件箱那栏仍是中文。

## 已知风险

**SWC plugin 是这套方案唯一的真实风险点。** 它 experimental、与 `@swc/core` 无 semver
保证、且与 React Compiler 有插件顺序冲突（Next 无法控制顺序，本仓目前没开 React Compiler）。

**升 Next 时必须复验 macro 能否编译**——这条要写进 `toolchain.md`。真炸了有两条退路：
钉住 Next 版本等 plugin 跟上，或切到「不用 macro」的写法（见上）。

## 附：spike 怎么做的

清理掉了，不入库。复现步骤：

1. `cd docs && pnpm add -w @lingui/core @lingui/react` + `pnpm add -w -D @lingui/cli @lingui/format-po @lingui/swc-plugin`
   （`docs/` 自己就是 workspace 根，`packages: - .`，所以要 `-w`）
2. `next.config.mjs` 加 `experimental: { swcPlugins: [["@lingui/swc-plugin", {}]] }`
3. 写一个 `"use client"` 组件用 `useLingui()` 的 `t` 与 `<Trans>`，挂到任意真实页面上
   （不挂的话 Turbopack 根本不编译它，等于没测）
4. 外面包一个模块级 `load`+`activate` 的 `I18nProvider`
5. `pnpm build` → 看 `out/app/<页>/index.html` 里的文案
6. 建 `lingui.config.ts` → `pnpm exec lingui extract` / `compile`
